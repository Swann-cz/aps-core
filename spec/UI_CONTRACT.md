## 1. 范围

本阶段界面只有三页，其余旧页面在导航和路由里隐藏（文件保留、不删）：

| 页面 | 路由 | 做什么 |
| --- | --- | --- |
| 年度总览 | `/annual-overview` | 看一份方案的全年计划：年度日历、月度事实、车型年度 PR / FOK / 缺口、判定结论 |
| 月度 Filling | `/monthly-filling?month=YYYY-MM` | 看一个月逐日、逐车间、逐车型的流量和在制 |
| 排产条件 | `/planning-conditions` | 增删改本方案的条件（IO_CONTRACT §2.1 八种，rev 17 加“指定开始生产”），保存后点“运行”重算 |
| 新建排产 | `/new-plan` | rev 5：上传销售计划（及可选的期初在制、生产行事历）建新方案，见 §8 |
| 正式版本 | `/formal` | rev 5：已定稿的计划列表，只读查看，见 §8 |

三页共用顶栏：方案选择、方案状态（见 §4 `state`）、“运行”按钮、“另存为新方案”按钮。默认路由 `/` 进年度总览。
没有登录、没有多用户、没有锁定 / 实绩 / 滚动（第二阶段再接）。

## 3. 方案目录 `workspace/scenarios/<id>/`

| 文件 | 内容 |
| --- | --- |
| `meta.json` | 见下 |
| `input.json` | IO_CONTRACT §2 输入；改条件只改其中 `conditions` |
| `plan.json` | 最近一次成功运行的计划（可不存在） |
| `verdict.json` | 与 `plan.json` 配对的判定（可不存在） |
| `run.log` | 最近一次运行的生成器和判定器标准输出 + 标准错误 |

```jsonc
// meta.json
{
  "id": "gap-sat",                    // 目录名；新建时用 "s-" + YYYYMMDD-HHMMSS
  "name": "gap 加三个周六",
  "created_at": "2026-10-25T10:00:00",
  "input_rev": 3,                     // 每次保存条件 +1
  "plan_input_rev": 3,                // 当前 plan.json 是用哪个 input_rev 算的；无计划为 null
  "run": { "state": "IDLE", "started_at": null, "finished_at": null, "seconds": null, "error": null }
                                      // state：IDLE / RUNNING / FAILED；error 一句话
}
```

## 4. 接口（前缀 `/api`，JSON）

| 方法 + 路径 | 请求 | 返回 |
| --- | --- | --- |
| `GET /api/scenarios` | — | `[ScenarioSummary]`，按 `created_at` 倒序 |
| `POST /api/scenarios` | `{ "from_id", "name" }` | 新方案的 `ScenarioSummary`；复制 `input.json`，不复制计划 |
| `GET /api/scenarios/{id}/conditions` | — | `ConditionsView` |
| `PUT /api/scenarios/{id}/conditions` | `{ "conditions": [...] }` | `ScenarioSummary`；整表替换 `input.json` 的 `conditions`，`input_rev` +1 |
| `POST /api/scenarios/{id}/run` | — | `ScenarioSummary`（`state` = `RUNNING`）；后台运行，见 §5 |
| `GET /api/scenarios/{id}/annual` | — | `AnnualView`；无计划返回 404 |
| `GET /api/scenarios/{id}/monthly?month=YYYY-MM` | — | `MonthlyView`；无计划或月份不在计划期返回 404 |

错误：方案不存在 404；该方案或任何方案正在运行时再点运行、或运行中改条件 409；返回体 `{ "detail": "<中文一句话>" }`。

```jsonc
// ScenarioSummary
{
  "id", "name", "created_at",
  "state": "NO_PLAN",                 // 下表五选一，前端顶栏按它显示
  "run": { ...meta.run },
  "plan_status": "FEASIBLE",          // plan.json 的 status；无计划 null
  "verdict": "ACCEPT",                // verdict.json 的 verdict；无判定 null
  "hard_error_count": 0,
  "objective": { "L1a": 0, ... }      // 取 verdict.json 的 objective；无判定 null
}
```

| state | 条件 | 顶栏显示 |
| --- | --- | --- |
| `RUNNING` | `run.state` = RUNNING | 运行中（已用秒数，前端每 3 秒刷新列表） |
| `FAILED` | `run.state` = FAILED | 运行失败 + `run.error` |
| `NO_PLAN` | 无 `plan.json` | 尚未运行 |
| `STALE` | `plan_input_rev` ≠ `input_rev` | 条件已改，计划未重算（仍显示旧计划） |
| `READY` | 其余 | 显示 `verdict` 与 `plan_status` |

## 5. 运行

1. 置 `run.state` = RUNNING，记 `started_at`。同一时刻全局只允许一个运行。
2. 子进程 `python -m engine <input.json> <plan.next.json>`，cwd = 仓库根，输出追加到 `run.log`。
3. 退出码 0 且 `plan.next.json` 的 `status` 为 `FEASIBLE` 或 `UNKNOWN`：再跑 `python -m judge <input.json> <plan.next.json> <verdict.next.json>`。
4. 成功（生成器退出码 0，且需要判定时判定器退出码 0）：`plan.next.json` → `plan.json`，`verdict.next.json` → `verdict.json`（没跑判定则删除旧 `verdict.json`），`plan_input_rev` = 运行开始时的 `input_rev`，`run.state` = IDLE。
   生成器状态为 `INPUT_INVALID` / `PROVEN_INFEASIBLE` / `EXECUTION_ERROR` 也算“成功写出”，照样替换，界面显示该状态和 findings。
4a. 热启动与安全网（rev 10）：已有 `plan.json` 且其 status 为 FEASIBLE/UNKNOWN、days 非空时，第 2 步加 `--warm-start <plan.json>`，`meta.run.warm_start` = true。新计划判定完后，再用新 input 判定旧 `plan.json`（→ `verdict.prev.json`）：旧计划 ACCEPT，且新计划不是 ACCEPT 或旧计划 objective 按字典序（L1a…L6）严格更好时，保留旧 `plan.json`、`verdict.json` 换成旧计划的新判定，`meta.run.kept_previous` = true，页面在运行状态旁显示灰字“新结果没有更好，沿用上一版计划（已按新条件重新判定）”。代价：同样的条件可能因上一版不同而得到不同计划。
5. 任何一步退出码非 0：`run.state` = FAILED，`error` = “生成器异常退出”或“判定器异常退出”，旧 `plan.json` / `verdict.json` 不动。
6. 后端启动时把残留的 RUNNING 改成 FAILED（`error` = “后端重启，运行中断”）。

## 6. 显示口径（后端计算）

记号：月份 mo 取计划期内的自然月；“累计”一律从 horizon.start 起算；车型集合 = `demand.PR` 的键；
`ratio` = `rules.monthly_band_ratio`；节点合计 = 该节点各车型之和。阶段以 `verdict.phases` 为准，无判定时用 plan 的 `phase`。

日的**主模式** `mode_summary`：当天五个车间里 `factory.modes` 小时数最大的模式；全部 OFF 则为 `OFF`。
日的**条件** `conditions`：覆盖当天的条件 `[ { "id", "type" } ]`；有 `date` 的按单日，有 `start`/`end` 的按区间，`PRE_STOP_TARGET` 按 `pre_stop_date`。

```jsonc
// AnnualView
{
  "scenario": ScenarioSummary,
  "horizon": { "start", "end" },
  "totals": {
    "annual_pr": 0, "annual_fok": 0, "annual_gap": 0,     // Σ车型；gap = Σ车型 max(0, PR 全年 − FOK 全年)
    "production_days": 0,                                 // 任一车间非 OFF 的天数
    "saturday_days": 0,                                   // 非 is_working_capable 但有车间非 OFF 的天数
    "overtime_days": 0                                    // 有车间模式 ∉ {OFF, default_mode} 的天数
  },
  "models": [ { "model": "A", "annual_pr", "annual_fok", "annual_gap",
                "months": { "2026-03": { "pr", "fok", "cum_gap", "band_short" } } } ],
       // cum_gap = max(0, 累计 PR − 累计 FOK)，到月末；band_short = max(0, 累计 PR − ratio × PR(m,mo) − 累计 FOK)
  "months": [ { "month": "2026-03",
                "pr", "fok", "ws",                        // 当月合计（ws = 当月 WS_daily 之和）
                "cum_gap", "band_short",                  // Σ车型
                "fin_eom",                                // 月末日成品库存合计（fin）
                "wip_eom": { "BS1": 0, ..., "AS_FIN": 0 },// 月末日 eod 节点合计
                "weld_days": { "BS1": 0, "BS2": 0 },      // 当月该线 in 或 out > 0 的天数
                "saturday_days", "overtime_days",         // 口径同 totals，限当月
                "phases": ["CHANGEOVER"] } ],              // 当月出现过的非 NORMAL 阶段（拆开 +，按 IO_CONTRACT §6 顺序）
  "days": [ { "date", "is_working_capable", "fok",        // fok 合计
              "mode_summary", "phase", "conditions" } ],
  "stop_list": [ ... ],                                   // plan.json 原样
  "findings": [ ... ],                                    // plan.json 原样
  "hard_errors": [ ... ]                                  // verdict.json 原样，最多前 50 条；无判定 []
}
```

```jsonc
// MonthlyView
{
  "scenario": ScenarioSummary,
  "month": "2026-03",
  "models": ["A", "B"],
  "targets": { "BS1": 69, ... },                          // input.wip_targets 原样（基础目标，不含 WIP_TARGET 条件）
  "days": [ {
    "date", "is_working_capable", "phase", "conditions",
    "mode_summary", "hours_max",                         // rev 3：主模式（口径同年度视图）、五个车间小时数最大值
    "workshops": {                                        // BS1、BS2、PS、AS_MAIN、AS_FIN
      "BS1": { "mode", "hours", "jph",                    // jph = factory.workshops 原样
               "bod", "in", "out", "eod",                 // 合计
               "in_cum", "out_cum",                       // 合计，累计
               "by_model": { "A": { "bod", "in", "out", "eod" } } } },
    "buffers": {                                          // WBS、PBS
      "WBS": { "bod", "in", "out", "eod",                 // in = 上游车间 out 之和；out = 下游车间 in
               "by_model": { "A": { "bod", "in", "out", "eod" } } } },
    "fin": { "fok", "fok_cum", "ws", "ws_cum", "eod", "bl",   // 合计；eod = fin，bl = 累计欠交
             "by_model": { "A": { "fok", "ws", "eod", "bl" } } }
  } ]
}
```

`by_model` 里每个车型都列出（0 也写），`models` 顺序 = 车型名排序。

## 7. 前端显示要求

- **年度总览**：沿用旧版布局。左侧年度日历按 `mode_summary` 着色（OFF / 默认模式 / 其他加班模式三档，非可生产日（`is_working_capable` = false）但当天有生产的日子另加“加”角标；普通周六不加标记）；rev 4：阶段 ≠ NORMAL 的日子在格子里加阶段短标签（停线、清线、复线、停前、换型、首启、退出、排空，与月度 Filling 列头同色同字），多个阶段时按 IO_CONTRACT §6 顺序取前两个；图例补上这些标签；
  点日期弹抽屉：阶段（中文名，见下表）、当天条件、当天所在的停线窗口（来自 `stop_list`）、“打开当月 Filling”。
  右侧摘要用 `totals`；下方按月趋势图（PR / FOK / WS）、月末成品库存柱图、月度事实表（`months`）、车型年度表（`models`，可展开 12 个月）。
  顶部：判定结论（ACCEPT 绿 / REJECT 红 + 硬错误数，可展开 `hard_errors` 前 50 条）、目标八级数值表、`findings` 列表。
  旧版的“锁定状态”“计划健康度”“产能余量”“WIP 偏差”不显示。
- **月度 Filling**（rev 3：按旧版 V6.1.4 的 Filling 样式，求“一屏能读”）：月份可前后切换；行 = 指标，列 = 日期，右侧固定一列“月度合计”（只对 IN / OUT / FOK / 交付类行求和，其余行显示 —；这是界面唯一允许的计算：把当月各日显示值相加）。
  - **左侧两列标签**：第一列“区段”（同组合并单元格），第二列“指标”。
  - **列头**：日期（MM/DD）+ 星期；阶段 ≠ NORMAL 时加阶段中文短标签（停线、清线、复线、换型、停前、首启、退出、排空），当天有条件加条件标签（类型中文名，超过两个显示 +N，悬停看全部）。阶段和条件不再占行。
  - **区段与行**（默认 33 行左右）：
    | 区段 | 指标行 |
    | --- | --- |
    | 生产参数 | 模式（`mode_summary` 中文名）、小时（`hours_max`） |
    | 焊装 Body Shop | BS1 投入、BS1 投入累计、BS1 产出、BS1 产出累计、BS2 同四行 |
    | WBS 缓冲区 | 日初、投入、产出、日末（目标 N） |
    | 涂装 Paint Shop | 日初、投入、产出、日末（目标 N） |
    | PBS 缓冲区 | 日初、投入、产出、日末（目标 N） |
    | 总装主线 | 日初、投入、产出、日末（目标 N） |
    | 总装完成线 | 日初、投入、FOK（产出）、日末（目标 N） |
    | 在制与成品 | BS1 日末（目标 N）、BS2 日末（目标 N）、交付（WS）、成品库存、欠交 |
  - **按车型子行**：WBS 至总装完成线各组的投入、产出、日末行可展开车型子行，默认收起。
  - **分组显示条**（表格上方）：每个区段一个开关按钮，加“展开全部”“收起全部”，同旧版。
  - **底色**：非可生产日列灰底；阶段含 STOP 的列淡橙底；含 BS_CLEAR 的列淡蓝底；含 REFILL 的列淡绿底。
  - 不再显示每个车间各自的模式 / 小时 / JPH 行，不提供单元格编辑。
  - **rev 18（2026-11-11 排产人员试用反馈 PPT 第 1–4 页）**，取代上面区段表里的对应行：
    1. **在制与成品**区段集中显示七个节点的日末，按物流顺序接在一起：BS1 日末、BS2 日末、WBS 日末、涂装日末、PBS 日末、总装主线日末、总装完成线日末（各行标签带“目标 N；上限 M”，同现有写法），然后是交付（WS）、欠交。方便一眼检查整条线的摆线情况。
    2. **WBS 缓冲区、PBS 缓冲区两个区段取消**：它们的日初、投入、产出不再显示，日末只在“在制与成品”里出现一次。分组开关条同步去掉这两个按钮。
    3. **涂装、总装主线、总装完成线**区段只保留投入、产出（完成线为 FOK）；日初、日末行去掉（日末已在“在制与成品”）。各车间的**投入累计、产出累计**（完成线为 FOK 累计）不放在各自区段里，统一放进表格最底部新区段“**累计**”：BS1 投入累计、BS1 产出累计、BS2 投入累计、BS2 产出累计、涂装投入累计、涂装产出累计、总装主线投入累计、总装主线产出累计、总装完成线投入累计、FOK 累计。焊装区段里原有的累计行也挪进这里。“累计”区段默认收起，可用分组开关展开。累计值用后端已有的 `in_cum` / `out_cum`，口径不变。
    4. **成品库存**行不显示：现在没有每日发车计划，库存数没有参考意义。后端字段保留，等有发车计划再显示。
    5. 按车型子行照旧：在制与成品里的共享节点日末、各车间投入产出可以展开到车型。
    6. 只改月度明细页；微调页的月表不变。
- **排产条件**：表格列出 `conditions`（编号、类型中文名、日期、车间 / 节点、数值、备注），新增 / 编辑用抽屉表单，字段按 IO_CONTRACT §2.1 表随类型切换，
  下拉选项来自 `ConditionsView`；删除需确认；“保存”调 PUT，保存后提示“已保存，点运行重算”。
  运行后生成器若返回 `INPUT_INVALID`，在本页顶部显示 `findings`。

  "conditions": [ ... ],                                   // input.json 原样

    "horizon": { "start", "end" },

    "nodes": ["BS1", "BS2", "WBS", "PS", "PBS", "AS_MAIN", "AS_FIN"],
    "auth_modes": ["SINGLE_8P2", "DOUBLE_SHIFT"]           // factory.modes 去掉 OFF 和 default_mode
  }

## 9. 缺口与建议（rev 7，2026-10-26，Swann 选方案 B）

目的：计划欠产时，告诉排产员“下一步该加哪些周六或加班”。做法是先把候选周六和加班一次性加成“候选授权”，运行一次，由生成器挑用量最少的；跑完显示实际用到哪些，一键删掉没用到的。引擎不改：周六授权、模式授权本来就由排产员给出，生成器在 L1 缺口最小的前提下按 L3 尽量少用（先平日加班、后周六，CORE_MODEL §6 已确认）。

### 9.1 缺口口径

取年度总览同一口径（§6 `annual` 的 `models[].months`）：某月任一车型 `band_short` > 0（低于月度带下限，计入 L1c），或计划期最后一个月任一车型 `cum_gap` > 0（全期欠产，L1a），即为**缺口月**（rev 9）。月末累计缺口在月度带以内是 C12 允许的，不算缺口，`gaps` 不列。没有计划、或 `state` ≠ READY（含 STALE）时不算缺口，面板提示“先运行一次，才能看缺口”。

### 9.2 候选授权池（后端按规则生成，不求解）

- 窗口：每个缺口月 M 取 M 的前一个月和 M 本月，并起来去重，截到计划期内。
- 候选周六：窗口内每个周六 d，同时满足——日历不可生产（`is_working_capable` = false）；前一天（周五）日历可生产（排除长假里的周六）；d 不落在当前计划 `stop_list` 的任一窗口内，也不落在任何 `SHUTDOWN` 条件范围内；已有覆盖 d 的非候选 `SATURDAY_AUTH` 时跳过。每个周六一条：`{ "id": "CAND-SAT-YYYYMMDD", "type": "SATURDAY_AUTH", "date": d, "reason": "候选（缺口建议）" }`，不写 workshops（= 五个车间）。
- 候选加班：模式按工时从低到高逐档升级（rev 9）。`meta.suggest_tried` 记录每次**采纳**过的 `{ "mode", "months": [...] }`（撤销不记）。本次取 `factory.modes` 中工时高于默认模式的各档里，工时最小、且本次窗口月份**不全在**同档已试记录里的那一档（现输入依次为 SINGLE_8P2 → SINGLE_8P3 → DOUBLE_SHIFT）；只为不在该档已试记录里的窗口月份生成。没有这样的档、也没有新的候选周六时，不能生成（stage = EXHAUSTED）。窗口内每个月一条：`{ "id": "CAND-OT-YYYYMM", "type": "MODE_AUTH", "mode", "start": 该月计划期内首日, "end": 末日, "workshops": 五个车间, "reason": "候选（缺口建议）" }`。
- id 以 `CAND-` 开头的条件就是候选；条件表里这些行带“候选”标签。
- 生成时在 `meta.json` 记 `"suggest": { "baseline": { "L1a", "L1b", "L1c", "L3a", "L3b" }, "created_rev": 生成后的 input_rev }`，baseline 取生成前 verdict 的 objective。

### 9.3 使用情况（跑完后）

只在条件里有候选、且 `state` = READY 时计算：
- 候选周六“用到”= 计划当天任一车间 mode ≠ OFF。
- 候选加班“用到的日子”= 范围内、`workshops` 中任一车间当天 mode = 该候选的 mode；同时记下每天用到的车间。
- 缺口对比：baseline 与当前 verdict 的 L1a、L1c、L3a、L3b。

### 9.4 采纳与撤销

- **采纳**（只在 9.3 能计算时可用）：删掉没用到的候选；用到的候选周六改 id 为 `SAT-YYYYMMDD`，reason 改为“补缺口（建议采纳）”；用到的候选加班按“连续用到的日子”切成段（五个车间全天 OFF 的日子跳过、不算断开；某天有车间开工却没用这个模式就断开），每段一条 `MODE_AUTH`：id `OT-<起始YYYYMMDD>`，start/end = 段首尾，workshops = 段内用到过的车间并集，mode 不变，reason 同上。id 冲突时末尾加 `-2`、`-3`。整表保存，`input_rev` +1，删除 `meta.suggest`，并把本次候选加班的 `{ mode, months }` 追加到 `meta.suggest_tried`。现有计划只用到了保留下来的授权，对新条件依然成立：采纳后**不重跑生成器**，只用新的 input 对现有 `plan.json` 重跑一次判定器（几秒）；判定 ACCEPT 则写回 `verdict.json`、`plan_input_rev` = 新 `input_rev`（状态 READY，计划不变）；判定不是 ACCEPT 则撤回这次采纳（条件和 meta 恢复原样），返回 409“采纳后判定未通过：<首条错误>”。
- **撤销**：删掉全部 `CAND-` 条件，删除 `meta.suggest`，`input_rev` +1。
- 条件里已有候选时不能再生成（409“已有候选授权，先采纳或撤销”）。正式方案三个写接口一律 409。运行中 409。

### 10.3 每一步的内容

每一步一张卡片：一句话说明这一步做什么，一个**主按钮**（大号，见 10.4），最多两个次按钮。不显示 L1a 等级别代号。

1. **导入**：年份 → “下载模板”（可选预填来源方案）→ 拖放区上传填好的 xlsx。**选好文件即自动预检**，不再单独点“预检”。预检通过：显示汇总（每车型全年需求、交付、期初在制、可生产天数、带入的条件数），主按钮“创建方案，下一步”；不通过：逐条列出错误（表名、行号、说明），主按钮变为“重新选择文件”。“分文件导入”（三份老格式文件）收进页面底部折叠区“其他导入方式”，默认收起。
2. **检查**：并入第 1 步，不单独成卡片。
3. **排产条件**：显示已带入的条件数和条件清单（只读简表：类型中文名、日期、车间、数值），次按钮“去排产条件页修改”（跳 `/planning-conditions`，改完回向导）；主按钮“开始排产”。STALE 时上方黄条“条件已改，需要重新运行”。
4. **运行**：运行中显示大号计时“已用 N 秒”和一句“一般 1–3 分钟，期间可以离开本页”，不可点主按钮；运行结束自动进入下一步。失败或没排出计划：红色结论“没有排出计划”+ `findings` 逐条列出，主按钮“回到排产条件”，次按钮“重新运行”。
5. **补缺口**：顶部**结论卡**（见 10.5），下方复用 §9.6 的“缺口与建议”卡片内容和按钮（生成候选、运行、采纳、撤销）。EXHAUSTED 时次按钮“仍然定为正式版”（进入第 6 步）。

## 11. 排产微调（rev 13，2026-11-09，Swann 确认）

在一份已有的排产上手动修改，即时看到连锁结果。类比：生成器是“自动运行”，微调是“手动点动 + 联锁检查”。第一期只做“加 X 台 / 抽 X 台”，其余工具留到第二期（见 11.9）。

### 11.1 四项取舍（Swann 2026-11-09 确认）
1. **改动方式**：直接改现有计划，用模板回放重算受影响的那一小段，不重新求解全年。
2. **连锁影响**：第一期只做严格模式。只重算被改的段和紧邻的停线、补线，其余日子保持不动；别处因此违规的，标红说明，不自动修。
3. **第一期工具**：加 X 台、抽 X 台、改当天产能（11.11，2026-11-09 增补）、撤销 / 重做、改前改后对比、停线卡片。规则分档见 11.10。
4. **页面**：新开“微调”页（左侧导航“微调”，路由 `/tuning`），复用年度总览的月度表，以及月度明细的数据，月表改为横向。

### 11.2 微调版本
- 从一个有计划的方案点“开始微调”：后端把该方案目录复制为新方案 `t-YYYYMMDD-HHMMSS`，名称 = 原名称 +“（微调）”。
  - `meta.json` 加 `"tuning": { "source_id", "created_at", "steps": [Edit...], "cursor": N }`，`cursor` 是当前生效到第几步，用于撤销 / 重做；
  - 每一步的结果存为 `tuning/step-<n>.plan.json` 和 `tuning/step-<n>.verdict.json`；`plan.json`、`verdict.json` 始终是第 `cursor` 步的结果。
- 微调方案隐藏“运行”按钮：重新求解会丢掉手改的内容。要重排，就“另存为新方案”。
- 判定为接受时，可以照 §8.2 定为正式版。
- `ScenarioSummary` 增加 `"tuning": null | { "source_id", "steps": N, "cursor": N }`；方案下拉框给它加“微调”标签（紫色）。

### 11.3 改动的定义（Edit）
```jsonc
{ "type": "ADD" | "REMOVE",
  "line": "BS1", "model": "A",
  "segment_end": "2026-03-25",     // 要改的生产段，用改前的段末日标识（该线该车型最后一个焊装进线 > 0 的日子）
  "quantity": 20 }                 // 正整数，单位：焊装进线台数
```
- **ADD**：加在段末那天的焊装进线上。当天放不下的部分顺延到后面的工作日：
  - 每多开一天，前面那天按当天能力满产，新的段末日承担零头；
  - 下游各车间按现有模板规则同日流转。
- **REMOVE**：从段末日的焊装进线里减。段末日减到 0 后，前一天变成段末日、承担零头，依此类推。
- **按停线类别的限制**（规则全部来自 CORE_MODEL，由模板执行；这里列出的是界面要讲清楚的结果）：
  - 段后是短停：停前日焊装进线 ≤ 当天整链能力 − PS 降幅（例：80 − 16 = 64）；降幅另见 SEGMENT_PLAN §12.1 的尾差合法条件。
  - 段后是长停清线：清线段有车就满产、零头放在清线前一天，所以只能按整天变化。实际台数**沿改动方向取整到整天**：加则向上取整，抽则多抽到整天，不会取成 0。告诉排产人员“实际 +Y”或“实际 −Y”。（2026-11-09 TUNE-1 验收后明确）
  - 段后不成停线（零流 ≤ 2 天）：没有额外限制。
  - 任何情况下都不能超过月度带上限（C12）、物理上限、胶龄。
- **不可行**时不改计划，返回原因和最近的两个可行台数（更少的一个、更多的一个），界面直接给出这两个按钮。
  - 原因要写到具体规则和数字，例如：“超过 3 月月度带上限 1144 台，这一段最多还能加 0 台”“短停前一天焊装最多进 64 台”“3/17 焊出的 29 台到复工超过胶龄 14 天”。
  - 预览和应用一次都要在 2 秒内返回：最近可行台数先按规则算出，再用回放核对，不逐台去试。

### 11.4 重算范围（严格模式）
- **起点**：被改段里第一个流量会变化的日子。
- **终点**：之后第一个“新旧计划各节点日末在制完全相同”的日子；通常是下一段补线结束、全链回到目标的那天。
- 起点到终点之间用模板逐日回放，终点之后的流量照抄原计划。累计完成、成品、欠交随之重算。
- 到下一次停线结束仍不收敛时，不改计划，返回“改动影响超过一段，第一期不支持”。
- 改完交判定器。判定不接受时，照样保存这一步，页面标红并列出硬错误。

### 11.5 计算顺序
1. 停线计算器（`engine/stop_calc.py`）先给即时估算：新的段末日、零流天数、清线与否、离门槛的距离。
2. 再用模板回放出新计划，交判定器判定。
3. 估算与回放不一致时以回放为准，页面上显示一行灰字“估算与精算不同，已按精算”。估算在真实数据上约 87% 一致，见 SEGMENT_PLAN §12.9。

### 11.10 规则分档：红线 / 黄线（2026-11-09，Swann 确认；取代 11.3、11.4、11.8 里“不可行”与“判定不接受”的口径）
微调体现的是排产人员的实际需求，比如为减少一次清线而让某月超出月度带。所以微调只死守物理和工艺规则，计划类规则允许突破，但要明示。生成器不受影响，自动排产仍守全部规则。

| 档 | 条款 | 微调中的处理 |
| --- | --- | --- |
| **红线** | C1 守恒、C2 产能、C4 单班焊装、C5 车型绑线、C6 物理上限、C7 胶龄、C14 满负荷生产段、C16 换型先进先出、C17 无投入不出车；§5 清线与补线状态机 | 工具不让做：引擎预检不通过就返回不可行，给出原因和最近可行台数；判定器报出的红线违规标红，不能定为正式版 |
| **黄线** | C3 日历与授权、C8 七节点下限、C9 WBS 经验带、C10 年度闭合、C11 交付时点、C12 月度带、C13 空闲许可、C15 | 照做，逐条列出偏差及台数（例：“3 月超月度带上限 80 台”“全年多做 80 台”“3/20 PS 日末低于目标 12 台”）；可以定为正式版，定稿时必须填理由 |

- 判定器条款代码的归档：红线 = `C1 C2 C4 C5 C6 C7 C14 C16 C17 SEQ BS_CLEAR PS_PRE_STOP REFILL CHANGEOVER INITIAL_DRAIN FIRST_START INPUT`；黄线 = `C3 C8 C9 C10 C11 C12 C13 C15 C18 FIXED START MODEL_QTY`（C18 加班开启条件，rev 16 补；START 指定开始生产、MODEL_QTY 指定时段产量，rev 17 补）。判定器以后新增的条款代码默认归红线，由 Claude 在本表补录。
- **C14 怎么调**：C14 要求生产段中间不能有不满产的日子。如果排产人员确实要让某天少做，可以用“改当天产能”（11.11），把那天的能力降下来，这样少做的那天就算满产，C14 照样成立。
- **引擎**：`apply_edit` 的预检和 `nearest` 只按红线算。黄线不拦，算出偏差放进 `warnings: [{rule, date, detail, amount}]`。
  - `warnings` 只列**相对第 0 步新增或变大**的偏差：同条款、同节点、同车型、同月份的偏差，第 0 步已有且台数没有变大的不列；变大的列出，detail 写“原 X 台 → 现 Y 台”（2026-11-09 打包实测补：示例计划原有的偏差被当成本次改动造成的）。
  - 只列判定器也会报成黄线的偏差（rev 13.6，取代 13.5 对下限缺口的写法）：C12 只看超上限；C10 只看全年多做；C13 只看相对第 0 步**新出现的违规空闲日**：包括新空出来的日子，也包括第 0 步就空着、但改动后失去合法理由的日子（例：抽台后“需求已排完”不再成立）；第 0 步已经违规的同日同节点不重复列（rev 16，2026-11-11 Swann 确认，取代“只看新出现的空闲日”）。C18 同理，只列新出现的“有空闲工作日却加班”。低于月度带下限、全年少做属于目标缺口（L1c、L1a），不是违规，不进 `warnings`；少做多少已由 `months` 的完成变化体现。
  - rev 14.1（CHECK-1gh 后明确）：C11 累计欠交是目标 L1b，判定器只查成品 / 欠交账目是否自洽，不把欠交当违规，引擎 warnings 不列欠交。改动范围外逐日流量不变，不会出现新的空闲日，但已有空闲日的“需求已排完”理由可能因累计完成变化而失效，所以跨月也按累计量推算这类 C13（rev 16，取代“不推算 C13”）。
  - **跨月黄线**（rev 13.7，第二期 A2）：改动范围外的日子流量不变，但累计完成会整体平移。引擎在改动范围外、到计划期末，按“改后累计完成 = 改前累计完成 + 本次增减”逐日推算 C10 全年多做、C12 超上限、C13 新出现的空闲日（空闲日判定口径与范围内相同，只用累计量，不重放），同样只列相对第 0 步新增或变大的。
  - **最近可行台数**（rev 13.7，第二期 A1）：不可行时 `nearest` 给出两个数：不超过请求的最大可行台数、超过请求的最小可行台数（找不到的那一侧省略）。覆盖所有红线原因，包括“短停前一天焊装最多进 N 台”（此时可行台数 = 当天上限内的部分，或跨过门槛改成整天的台数）。按规则直接算，不暴力回放；每次 apply_edit 仍 < 2 秒。
- **预览是否同时跑判定器**（rev 16，2026-11-11 Swann 确认按建议）：先测全年计划判定一次的用时；1 秒内就在预览时也跑判定器，预览的红黄线直接用判定结果，引擎手写预检只用于给原因和最近可行台数；超过 1 秒则保留引擎预检，停止拖动后再补跑一次判定。测量结果和最终做法由 Claude 补进本条。
- **后端**：判定器照常报全部条款；后端按上表把 `hard_errors` 分成 `red_errors`、`yellow_deviations`，加进 `TuningImpact`。判定器不改。
- **全年表**：“可加”“可抽”各显示两个数：守全部规则的、只守红线的。
- **定为正式版**：
  - 红线违规为 0 才能定；
  - 有黄线偏差时，弹框列出全部偏差，必须填理由，理由写进 `meta.formal.note`；
  - 正式版列表加一列“偏差条数”。

### 11.10a 红黄线明细的合并与页面显示（2026-11-09 二次联调补）
- **合并**：判定器逐日、逐节点各报一条，同一件事会出现几十条。后端返回 `red_errors` / `yellow_deviations` 前先合并：同条款、同节点、同车型、日期连续（中间只隔非生产日也算连续）的合成一条。`date` 取首日；`detail` 写“起止日期 + 节点中文名 + 车型 + 共 N 天 + 原说明”，节点和车型都要写出来（例：“04-29 至 04-30 焊装一线 A：可生产日空闲但需求未排完，共 2 天”）。`amount` 有就取各天最大值，没有就不写。
- **明细一行的写法**：页面每条只写“条款中文名 · detail”，不再在前面重复日期和节点（detail 里已有）；没有 `amount` 就不写台数，不出现“台数未返回”。节点中文名后端和页面用同一套（例：焊装一线，不写“焊装1”）。
- **说明去缩写**：判定器说明里的 `cumFOK`、`cumPR`、`FOK`、`PR`、`WS`、`WIP` 换成“累计完成 / 累计需求 / 完成 / 需求 / 交付 / 在制”；不要留下“cum完成”这类半中半英的写法，也不要出现“当月累计 累计需求”这类叠词（整词替换：“完成线 cumFOK”→“累计完成”，“当月累计 cumPR”→“当月累计需求”）。
- **页面顶部结论**（微调页），按当前步的 `red_errors` / `yellow_deviations` 判断，不用 `verdict`：
  - 有红线：红字“有红线违规 N 条，不能定为正式版”；
  - 无红线、有黄线：橙字“红线全部通过，黄线偏差 N 条（定稿时须说明理由）”；
  - 都没有：绿字“排出来了”。
  - 计算用时保留一位小数（例：“用时 0.8 秒”）。
- **预览面板**：预览时 `yellow_deviations` 就是引擎 `warnings`，只显示一块，标题“黄线偏差（预估，确定后以判定为准）”，不要同样内容出现两块。应用后显示判定器的结果，标题“黄线偏差（已校验）”。
- **定稿按钮**：`red_errors` 为空即可用（第 0 步也一样）；`yellow_deviations` 非空时弹框列出并要求填理由。

### 11.13 加班 / 周六（第二期，2026-11-09 Swann 确认“开了就用满”）

### 11.14 差额池（第二期，2026-11-09 Swann 确认：先建池子提醒缺口，不自动补平）

- 页面：状态条加标签“差额 +120 台”（不为 0 时橙底，写“未抵消”；全为 0 时绿底“差额 0”）；点开抽屉列出每一步的差额和改动内容，并提示“可选一段加台或抽台抵消”。
- 定稿不因差额池拦截（全年多做 / 少做已由黄线和目标说明）。
- MCP：`list_tuning_scenarios` 或单独的 `pool` 查询返回 `pool`，供 Copilot 提醒业务员。
- 自动补平（勾选“自动在后面补平”）留到以后，等差额池用顺手再做。

### 11.16 与公司 Copilot 智能体交换文件（rev 15，2026-11-10 Swann 选“上传文件”）
背景：公司的 Copilot 是微软的网页版（有自己的服务器，可以建智能体），连不到本机，基本用不了 MCP。所以排产系统和 Copilot 之间改用文件交换：系统导出“微调状况”文件，Copilot 回复“改动清单”，人把清单贴回页面逐步执行。§11.12 的 MCP 工具保留，但不在公司环境使用。

**流程**
1. 微调页状态条加按钮“导出给 Copilot”（只在微调方案下可用），下载 `微调状况-<方案 id>-第<cursor>步.txt`。
2. 排产人员在 Copilot 智能体里上传这个文件，并说出需求。智能体按《微调指令说明》v3（`spec/TUNE_COPILOT.md` 第 8 节）和人讨论，最后给出一个改动清单代码块。
3. 状态条加按钮“导入 Copilot 回复”：弹框里有一个大文本框（粘贴 Copilot 的整段回复，前后有文字也可以）和“选文件”（.txt / .json）。点“读取”后，后端解析出清单：
   - 有错误时，在弹框里逐条列出中文错误，不进入执行；
   - 没有错误时关闭弹框，右栏展开成“导入清单”。
4. 导入清单逐步执行：
   - 列出全部步骤（序号、中文描述、Copilot 的说明 `note`），当前步高亮；
   - 当前步自动选中对应的段或日子，填好台数，调 preview（月表跟着变，同 rev 14.2）；
   - 人看过预估后，点“确定”应用，或点“跳过”；不可行时只能“跳过”或手动改台数（同普通工具，可点“改为 N 台”）；
   - 应用或跳过后进入下一步。最后一步做完后显示小结（几步应用、几步跳过），点“结束导入”回到普通工具；中途也可随时点“结束导入”；
   - 每步的结果（已应用 / 已跳过 / 不可行）写在步骤旁。
5. 做完后再导出一次。文件里带上每一步的来源和实际台数，智能体据此向排产人员讲结果。

**状况文件 `aps-core/tune-context/v1`**
文件是 UTF-8 文本。前几行以 `#` 开头，是写给 Copilot 的中文说明，例如“本文件由排产系统导出，只含排产数字；改动清单格式见《微调指令说明》第 8 节”。后面是一个 JSON 对象：
```jsonc
{ "schema": "aps-core/tune-context/v1",
  "exported_at": "2026-11-10T15:20:00",
  "scenario": { "id": "t-20261110-072745", "cursor": 3, "steps": 3 },   // 不写方案名称（名称可能含自由文字）
  "horizon": { "start": "2026-01-01", "end": "2026-12-31" },
  "models": ["A", "B"], "lines": ["BS1", "BS2"],
  "modes": [ { "mode": "SINGLE_8H", "hours": 8, "default": true }, { "mode": "SINGLE_8P2", "hours": 10, "default": false } ],
                                      // factory.modes 去掉 OFF；供 OVERTIME 选档
  "non_working": ["2026-01-03", ...], // 计划期内 is_working_capable = false 的日子
  "phases": { "2026-01-01": "STOP", ... },  // 同 annual_phases，只列阶段 ≠ NORMAL 的日子
  "segments": [ { "line", "model", "start", "end", "tail_quantity" } ],   // 同 annual_segments
  "stops": [ StopCard ],              // 全年所有停线
  "months": [ { "month": "2026-03",
                "by_model": { "A": { "pr": 900, "fok": 880, "cum_pr": 2700, "cum_fok": 2690 } },
                "can_add_all", "can_remove_all", "can_add_red", "can_remove_red" } ],
  "pool": { "total", "steps" },       // 同 §11.14
  "red_errors": [ RuleIssue ], "yellow_deviations": [ RuleIssue ],   // 当前步
  "steps": [ { "step": 1, "edit": Edit, "actual_quantity": 80, "source": "PAGE" | "COPILOT",
               "note": "…", "delta": { "A": 80 }, "red": 0, "yellow": 1 } ] }   // cursor 以内的步
```
- 保密：只写排产数字和代号（日期、产线 / 车型代号、台数、阶段、规则偏差）。不写方案名称、设备名称、输入文件原文，也不写 `factory` 里 modes 以外的内容。
- `RuleIssue.detail` 已按 §11.10a 换成中文。

**改动清单 `aps-core/tune-batch/v1`**（Copilot 输出，人贴回页面）
```jsonc
{ "schema": "aps-core/tune-batch/v1",
  "based_on": { "scenario_id": "t-20261110-072745", "cursor": 3 },
  "request": "免掉 3 月清线，多做的从 4 月扣",     // 排产人员原话
  "edits": [
    { "edit": { "schema": "aps-core/tune-edit/v1", "type": "ADD", "line": "BS1", "model": "A",
                "segment_end": "2026-03-25", "quantity": 160 },
      "note": "加 160 台跨过清线门槛" },
    { "edit": { ... "type": "REMOVE", ... }, "note": "从 4 月那段抽回 160 台" } ] }
```
- 接口 `POST /api/scenarios/{id}/tuning/import`，请求 `{ "text": "整段回复" }`；返回 `{ "ok", "errors": [ "中文" ], "warnings": [ "中文" ], "batch": { "request", "base_cursor", "edits": [ { "edit", "note", "label", "ordinal" } ] } }`。只解析，不改任何文件。
- 解析：
  - 在文本中找含 `"aps-core/tune-batch/v1"` 的 JSON 对象：先找 ```json 代码块，再找第一个配对完整的 `{…}`；
  - 中文引号、行尾逗号这类常见笔误不自动修，报错“清单格式不对：第 N 行附近”。
- 校验（任一条不满足就报错，`ok` = false）：
  - `scenario_id` 与当前方案不同：“这份清单是给另一个微调方案写的”；
  - `edits` 为 1–20 步；
  - 每步的 `edit` 按 §11.3 / 11.11 / 11.13 的必填字段检查：类型、日期格式、`quantity` 为正整数、`capacity` 为非负整数、`mode` 为 SATURDAY 或 `modes` 里的一档；
  - ADD / REMOVE 的 `segment_end` 必须是当前步某段（同产线、同车型）的段末日，否则报“第 N 步：BS1 / A 没有段末 03-25 的段”。
- `based_on.cursor` 与当前 cursor 不同：不报错，写进 `warnings`：“这份清单是按第 3 步写的，现在在第 5 步，请逐步核对”。
- `label`：后端写的一句中文，如“BS1 / A 3/25 那段加 160 台”“3/14 开周六”“BS1 3/18 产能改为 40 台”。
- `ordinal`（只 ADD / REMOVE 有）：该段在同产线同车型的段里按 `start` 排第几（从 1 起），按导入时的当前步算。
- 执行时找段：页面用当前 `annual_segments` 里同产线、同车型的第 `ordinal` 段。前面的步骤让段末顺延时，用顺延后的段末，并在步骤旁写“段末已从 3/25 顺延到 3/27（前面的步骤所致）”。如果同产线同车型的段数比导入时变了，就不猜：列出这几段让人选，或跳过。
- 应用时请求里的 Edit 带两个可选字段 `"source": "COPILOT"` 和 `"note"`（tune-edit/v1 只增字段，引擎忽略）。页面上的普通操作不带，按 `"PAGE"` 记。后端在 `meta.json` 的步骤记录里存下 `source`、`note` 和 `actual_quantity`，供导出使用。
